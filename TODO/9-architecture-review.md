# 9. Ревью кода, архитектуры и системного дизайна

> **19.11.2026.** Срез ветки `feat/mcp-reconcile` (= `main` + сверка в MCP). Находки с пометкой
> «проверено» подтверждены запросом к проду или чтением кода; остальное — оценка по коду.

## Итог в трёх строках

1. **Ядро торговли спроектировано хорошо**: слои domain / application / ports / adapters, один
   `PositionCalculator` на живого бота, бумажный режим и бэктест, 180 тестов бэкенда.
2. **Главные риски — не в торговой логике, а вокруг неё**: два сервиса открыты в интернет без
   авторизации, исследования (основа форвард-теста) не в git, нет бэкапов и алертов.
3. **Для реальных денег** есть два узких места: последовательная обработка тиков всех ботов
   и запись «биржа → БД» без страховки на обратный случай.

## Что сделано хорошо

- **Чистая архитектура в бэкенде.** `domain/` не знает про БД и биржу; биржи — адаптеры за портами
  (`ExchangeExecutor`, `MarketData`); бумажный режим — ещё один адаптер, без веток в стратегии.
- **Один источник правды для механики позиции.** `PositionCalculator` используют живой бот,
  исследовательские бэктесты и сверка (`replay.py`) — поэтому сверка LINK совпала до 0.03%.
- **Production-гигиена docker-compose**: все порты на `127.0.0.1`, вход только через nginx;
  комментарий про `--reload` и стёртое состояние ботов — хороший след прошлой аварии.
- **CI/CD**: тесты → образы с тегом `sha-…` → деплой, `.env` из секретов, ожидание health.
- **Восстановление после рестарта**: `restore_active_strategies` поднимает PYRAMIDING / WAITING /
  STRADDLE, планировщик сам подхватывает SIGNAL из БД.
- **Дисциплина форвард-теста**: ожидания и критерии записаны до первой сделки, изменения — датированными записями.

### P1. Тики всех ботов обрабатываются последовательно в одном цикле

- `backend/app/services/websocket.py:130`: `await self._update_strategies(symbol, price)` внутри
  чтения Redis pub/sub; внутри — по очереди `await engine.on_price_update`, а он ходит на биржу
  (добор, закрытие).
- **Риск:** пока один бот 1–3 с закрывает позицию на Bybit, все остальные не видят цену.
  Худший момент — каскад: 4 шорта на коррелированных альтах бьют стопы одновременно, и каждый
  следующий закрывается позже и хуже. В paper не видно (исполнение мгновенное), на реальных деньгах — проскальзывание.
- **Исправление (полдня):** у каждого движка своя `asyncio.Task` + «последняя цена» (коалесцирующий
  слот); слушатель Redis только кладёт цену и не ждёт. Порядок внутри бота сохраняется,
  между ботами — параллельно.

### P1. Вход «биржа → БД» без страховки на обратный случай

- `open_position.py:41` — рыночный ордер на бирже, `:87` — `commit` в БД. Если запись упадёт
  (БД недоступна, ошибка сериализации), позиция на бирже есть, а у бота — нет.
- Сверка с биржей (`strategy.py:336`) ловит только «в БД открыто, на бирже нет».
- **Исправление:** при ошибке после исполнения — немедленно закрыть позицию на бирже или
  записать её как «осиротевшую» и поднять алерт; плюс периодическая сверка «на бирже есть, в БД нет»
  по всем аккаунтам.

### P1. Нет алертов

- Loki + Grafana есть, но никто не узнает, что бэкенд упал, поток цен встал или бот ловит ошибки.
  MCP `bots_health` — только по запросу.
- **Исправление:** Grafana alerting по логам (`[ERROR]`, `[EXCHANGE_CLOSED]`, отсутствие `[TICK]`
  N минут) → Telegram. Или cron, который дёргает `/api/analytics/bots-health` и шлёт `problems > 0`.

### P1. `/health` всегда отвечает «healthy»

- `backend/app/main.py:86` — статический ответ. CI ждёт его после деплоя и считает деплой удачным,
  даже если не поднялся планировщик или Redis-слушатель.
- **Исправление:** `/health` проверяет БД, Redis, `signal_scheduler.running`, живость слушателя цен;
  подробности — в `/api/analytics/bots-health`.

### P2. Нет автоматических бэкапов БД

- Есть только ручной `pg_dump` в `deploy/README.md` (для переезда). Сделки, журнал разборов,
  история форвард-теста — на одном диске VPS.
- **Исправление (1 час):** ежедневный `pg_dump` cron → объектное хранилище / другой сервер, хранить 14 дней,
  раз в месяц проверять восстановление.

### P2. Долгоживущая сессия БД на каждого бота

- `websocket.py:182`: `AsyncSessionLocal()` создаётся при регистрации и живёт, пока бот в позиции
  (дни). Объекты в ней не видят изменений из API (поэтому «настройки применятся со следующей
  сделки»), а после ошибки сессия может остаться в плохом состоянии.
- **Исправление:** сессия на операцию (`async with AsyncSessionLocal()` в use case), состояние
  бота в памяти — явная структура, а не ORM-объект.

### P2. Один процесс — осознанное ограничение

- Состояние ботов, планировщик и поток цен живут в памяти одного uvicorn-процесса; деплой =
  рестарт = пауза в обработке тиков. Для одного пользователя это нормально, менять не нужно.
- **Но зафиксировать:** никогда не запускать backend с `--workers > 1` (два планировщика войдут
  дважды); у реальных ботов стоп должен стоять на бирже (сейчас есть страховочный — хорошо),
  чтобы рестарт не оставлял позицию без защиты.

### P2. Сервисы без тестов в CI

- `signals` (1430 строк) и `price-tracker` (361) — 0 тестов; backtester — только `test_indicators.py`.
  Фронтенд — только сборка (`next build` проверяет типы и линт, это уже немало).
- **Исправление:** минимум — smoke-тест импорта и основных роутов signals; price-tracker — тест
  публикации в Redis на подставном клиенте.

### P3. Фронтенд: монолитные страницы и `any`

- `app/bots/page.tsx` — 1509 строк (страница + 4 модалки + панели), `backtester/page.tsx` — 1288.
  68 мест с `any`. Опрос `/api/bots` каждые 5 с поверх WebSocket.
- **Исправление:** вынести модалки и карточку в `components/bots/`, тип `Bot` из схемы API
  (можно генерировать из OpenAPI FastAPI), опрос реже — WS уже приносит события.

### P3. JWT на 7 дней в `localStorage`

- `ACCESS_TOKEN_EXPIRE_MINUTES = 10080`, токен в `localStorage` (`frontend/lib/api.ts:24`).
  При XSS — полный доступ к аккаунту, включая управление реальными ботами.
- **Исправление:** короткий access-токен + refresh в httpOnly cookie. Не срочно, пока пользователь один.

### P3. MCP: токен в URL

- Достаточно для одного владельца; nginx не пишет `/mcp/` в лог. При расширении доступа — OAuth (`TODO/8`).

## Системный дизайн: рекомендации

```
                ┌──────── nginx (TLS) ────────┐
 browser ──────►│ /        → frontend          │
 claude.ai ────►│ /api/    → backend (1 proc)  │──► Postgres (trading)
                │ /mcp/<t> → kandle-mcp        │──► Redis ◄── price-tracker ◄── Bybit WS
                │ signals.    → signals  ⚠ open│──► Postgres (signals)
                │ backtester. → backtester ⚠ open──► Postgres (backtester)
                └──────────────────────────────┘
```

1. **Закрыть периметр** (P0): наружу — только `/`, `/api/`, `/mcp/<token>`, `logs.` за логином Grafana.
   `signals.` и `backtester.` — за паролем или только внутренняя сеть.
2. **Развести «торговое ядро» и «исследования» по ресурсам.** Бэктесты и живые боты на одном VPS —
   ок, но с лимитами: `deploy.resources.limits` (CPU/RAM) для `backtester-web`, чтобы прогон не
   отнимал процессор у backend.
3. **Обработка тиков — модель «актор на бота»** (P1 выше): очередь с последней ценой на каждого бота.
   Это же упрощает сессии БД и делает поведение бота детерминированным.
4. **Наблюдаемость = три сигнала:** тики идут (по монетам), планировщик проверяет сигналы, ошибок
   исполнения нет. Всё это уже считается в `bots-health` — остаётся слать алерт, когда `problems > 0`.
5. **Воспроизводимость решений:** код исследований в git + в журнале kandle ссылка на коммит
   скрипта, давшего цифры. Тогда любую цифру форвард-теста можно пересчитать.
